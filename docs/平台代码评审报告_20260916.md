## 0. 结论摘要

工程骨架完整、分层与设计文档基本对应，接口分区（A01–A06）齐全，16 项后端测试全部通过。但评审发现 **前端与后端契约系统性不一致，导致 `VITE_DATA_MODE=api` 模式下系统无法工作**，且存在 **时间戳字符串被错标为 UTC（比真实时刻早 8 小时）**、**"降尺度"为不实声明**、**公开位置可精确披露** 三类影响成果可信度的实质缺陷。当前可演示的只有 demo 合成模式；"已实现""已验证"的范围应据此下调。

需要强调：时间戳一条经复核后**已收窄口径** —— 数据库存储的时刻与主客观匹配逻辑是**正确的**，缺陷限于对外序列化的标注与前端展示（详见 C2 修订说明）。

按严重度分布：致命 3 项、严重 9 项、中等 11 项、轻微 12 项。

### C2. 序列化环节把非 UTC 时间标成 `Z`：输出字符串比真实时刻早 8 小时

> **本条已按用户 2026-09-16 的说明复核并修订口径。** 用户指出："从和风天气获取的是 UTC 时间，本地时间是北京时间"。复核结论：**数据存储与时刻语义是正确的，缺陷只在序列化/标注环节**，不涉及数据损坏。原表述"系统性偏移 8 小时"容易被误读为存错了，已改写如下。

**已核实为正确的部分（不必修改）**：

- `db/models.py:24` `utc_now()` 返回真正的 UTC（`+00:00`）；
- `weather_service.py:33` `parse_rfc3339_utc` 以 `astimezone(timezone.utc)` 归一化，Open-Meteo 请求显式带 `timezone=UTC`（`weather_service.py:98`）；
- 全部时间列均为 `DateTime(timezone=True)`（`TIMESTAMPTZ`），**存的是时刻（instant），不是墙上时间**；
- 实测入库值与国际口径一致：`weather_records.target_time` 最早值为 `2026-09-16 08:00:00+08:00`，即 **`2026-09-16 00:00 UTC`**，与 `上海更细气象产品调研_20260916.md:30` 记录的窗口起点"2026-09-16 00:00 UTC"完全吻合；
- UGC 侧前端发 `new Date().toISOString()`（真 UTC），后端按时刻存储，读回仍是同一时刻。

```
psql target_time            : 2026-09-16 08:00:00+08:00
psql AT TIME ZONE 'UTC'     : 2026-09-16 00:00:00        <- 真实 UTC 墙上时间
SQLAlchemy 读回             : 2026-09-16T08:00:00+08:00  <- 同一时刻
same instant as psql?       : True
-> 存储的时刻正确
```

**真正的缺陷**：代码用 `datetime.strftime("%Y-%m-%dT%H:%M:%SZ")` 格式化**带 +08:00 的对象**，把北京时间直接缀上 `Z`。`Z` 在语义上等于 `+00:00`，因此该字符串**指向另一个时刻**：

```
读回值                       : 2026-09-16T08:00:00+08:00
代码输出（strftime + 'Z'）   : 2026-09-16T08:00:00Z
同一时刻的正确 UTC 标注      : 2026-09-16T00:00:00Z

把 API 字符串按 UTC 重新解析 : 2026-09-16T08:00:00+00:00
实际存储时刻                 : 2026-09-16T00:00:00+00:00
MATCH? False ；delta = 8:00:00
```

**根因（实测）**：PostgreSQL 会话时区为 `Asia/Shanghai`（`SHOW TimeZone` 实测），`TIMESTAMPTZ` 读回即 `+08:00`；代码未先 `astimezone(timezone.utc)` 再格式化。

**影响面**：约 40 处 `strftime(...Z)`，遍布 `env_service.py`、`ugc_service.py`、`export_service.py`、`task_service.py`、`routers/*`。由于前端（浏览器）按 ISO 8601 规则把 `Z` 解析为 UTC 再转 `Asia/Shanghai` 显示，**界面时间比实际晚 8 小时**：`2026-09-16T08:00:00Z` 会被显示为北京时间 16:00，而该数据实际是北京时间 08:00。同一响应内 `meta.server_time`（走 `timezone.utc`）反而正确，二者互相矛盾，可自证 bug：

```
API view resolved_time = 2026-09-16T21:00:00Z   （DB 该行实为 13:00:00Z）
API meta.server_time   = 2026-09-16T12:48:01Z   <- 这个是对的
```

**与研究口径的关系**：设计文档 `后端应用接口层_详细设计.md:32` 明确要求"输出统一 UTC `Z`，前端转为 Asia/Shanghai"，`实时气象视图_详细设计.md:62` 与 `环境计算与空间分析层_详细设计.md:36` 均写"服务端统一 UTC"。因此 **UTC 输出口径是既定口径，不需要改口径**；需要修的是序列化实现。

**与数据源无关（重要）**：该缺陷与供应商是否为和风无关。无论上游返回 UTC 还是北京时间，只要读取路径拿到的是非 UTC 的 aware datetime，`strftime(...Z)` 就会错标。接入和风时仍须在入库前显式归一化为 UTC 并记录原始时区字段——而该归一化要求当前**没有**在接入层强制实现（`parse_rfc3339_utc` 仅在 `weather_service`/`ugc_service` 局部使用）。

**修正表述**：原报告"系统性偏移 8 小时""已污染导出文件表头"应改为更准确的 **"（a）存储与时刻语义正确；（b）API/导出字符串被错误标注为 UTC，比真实时刻早 8 小时；（c）导出文件表头 `target_time_utc` 名不副实，其值实为北京时间"**。主客观时段匹配因两侧都按时刻比较而**未错位**；受影响的是**对外输出的时间标注与前端展示**。

**处理方向**：新增统一序列化函数，先 `astimezone(timezone.utc)` 再格式化，替换全部约 40 处 `strftime(...Z)`；或将会话时区固定为 UTC；并在接入层强制"供应商时间→UTC"归一化并记录来源时区。补一条回归测试：断言 API 时间字符串按 UTC 解析后与库中时刻相等。

### C3. "0.25° 降尺度"为不实声明，实际是单点值全域复制

`env_service.py:239` 向 API 声明：

```python
"resolution": "0.25° (~25km) downscaled point",
```

但 `weather_service.py:90-99` 只以**一个坐标**（`SHANGHAI_CENTER_LON/LAT`）请求 Open-Meteo，`weather_service.py:178-179` 把该单点值写入**每一条** `WeatherRecord`。实测：

```
weather_records 每个 release 的 distinct(lon), distinct(lat) = 1, 1
导出文件 exp_b500954d2aaa.csv：168 行，distinct(longitude,latitude) = 1 组 (121.4737, 31.2304)
```

即：全上海任何点查询都返回同一个值，**不存在任何降尺度**。声称 "downscaled" 与项目规定"不通过插值制造空间信息""不宣称未完成的能力"直接冲突；`scene_service.py:24` 更把建筑图层声明为 `type="3dtiles"`，但全工程无任何 3D Tiles 服务（grep 仅得该声明本身），前端 `Cesium3DTileset.fromUrl` 无资源可载。

**处理方向**：删除 `downscaled` 措辞，`provenance` 如实写"单格点 0.25° 值，无空间降尺度"；图层类型改为与实际一致，或在实现切片服务前标 `unavailable`。

## 2. 严重问题

### H1. 默认即公开发布，且无内容审核门控

`init_db.py:32,44` 预置账号 `user_test/user123456`、`admin_test/admin123456`（README 第 2 节公开发布）；`schemas/check_in.py:26` `visibility` 默认 `"public"` —— 客户端**不传该字段即自动公开**。`ugc_service.py:179,424-426` 把 `publication_status` 直接置为 `"published"`，`UgcReport.status` 写入 `"pending"` 后无人消费。完整正文 `note` 经 `CheckInPublicItem.note` 向匿名用户全文暴露。

**建议**：默认 `private`；公开需显式确认；接审核队列后方置 `published`。

### H2. `public_location_precision="exact"` 可将精确坐标公开发布

`ugc_service.py:150-151` 允许请求指定 `exact`，随后 `:248` 公开投影直接返回该精确坐标。设计文档 §6.4 要求"精确公开必须明确确认"，代码无任何确认字段或权限门控，且与前端网格脱敏预期不符。

### H3. 环境视图与导出无所有权隔离

`env_views` 表无 `owner_id` 列（实测列清单确认）；`environment.py:55,79,92` 全部**无认证依赖**，"知道 view_id 即可读取任意环境数据"。`export_service.py:95` 的 `get_fixed_view` 同样不校验调用者。当前数据敏感度低，但作为系统权限模型是明确缺口。

### H4. 导出忽略时空范围参数并静默截断

`export_service.py:97-103` 只按 `release_id` 过滤并 `.limit(10000)`，请求体中的 `bbox`/`start_time`/`end_time` **从未使用**，超限不返回 422。设计文档 §9 要求"环境导出必须指定 view_id 和合法时空范围""超过限制返回 422，不静默截断"。

### H5. 导出幂等键被接收后忽略；删除后旧导出仍可下载

`exports.py:22,33` 接收 `Idempotency-Key` 并透传，`export_service.py:32` 声明该参数后**函数体内从未引用**，`ExportRecord` 无幂等列 —— 重复请求会创建多份导出，也无 409 路径。同时 `exports.py:71-81` 只校验所有者/状态/存在性/有效期，**不复查记录可见性**；`ugc_service.py:467` 软删除时不使既有导出失效，故已删除打卡仍可经旧导出下载，与设计文档 §6.1/§9 冲突。

### H6. 环境匹配不校验位置，注释与实现不符

`ugc_service.py:53` 注释写 "Find nearest weather record by time and location"，但 `:55-59` 仅按时间距离对**全表**排序，**无任何空间条件**。配合 C3（单点值全域复制）当前"碰巧"结果正确，但一旦接入真实格点数据即产生**错误匹配**，且 `matched_release_id` 无外键约束（`models.py:178` 为裸 `String`）。

### H7. `Geometry` 列从未写入，空间索引形同虚设

实测 `platform.ugc_check_ins`：14 行中 `count(geom_exact)=0`、`count(geom_coarse)=0`。表上已建 `idx_ugc_check_ins_geom_exact/geom_coarse` 两个空间索引，但应用只写 `exact_lon/lat`、`coarse_lon/lat` 标量列，几何列恒为 NULL。后果：PostGIS 空间能力完全未使用；任何基于几何列的查询/聚合都会**静默返回空集**；项目要求的"空间索引与可复核记录数"无法佐证。

### H8. 测试无隔离，直写生产库且不清理

`conftest.py:11-19` 直接对 `gis_thermal_shanghai` 执行建表与 `sync_weather_release`，测试数据不清理。实测累积：`ugc_check_ins=14`（含 `is_deleted=True` 残留）、`ugc_reports=3`、`env_views=8`、`export_records=7`、`user_sessions=16`、`weather_records=336`。测试还写死 `2026-09-01`/`2026-09-30` 区间，随日期推移会失效。测试"通过"不代表功能正确 —— 16 项全过，而 C1/C2/C3 均未被覆盖。

### H9. 认证与 CSRF 防护缺失

- `auth.py:45-48` `secure=False`、仅 `samesite="lax"`，且**登录取证响应体回传 `session_id`**，绕过 HttpOnly 的意义；
- `auth_service.py:82-83` 支持 `Authorization: Bearer`，完全绕过 cookie 与 CSRF；
- 前端 `api.ts:24` 会发送 `X-CSRF-Token`，**后端全工程无任何读取/校验**（grep `csrf` 无匹配），而设计文档 §7 明确要求"涉及状态变更的请求校验 CSRF token 与 Origin"；
- `main.py:52-57` `allow_origins=["*"] + allow_credentials=True` 是无效且危险的组合（浏览器会拒绝该组合，同时暴露意图），设计文档 §7 明文禁止"通配 CORS 配合凭据"。

`AGENTS.md` §4 与平台 `系统分层与模块架构.md:81` 均称"PostGIS 当前是计划部署，不表述为已经安装"。实测：
