# 实时热环境与UGC体感地图：原始设计

版本：v0.3（2026-09-16补充太阳辐射数据源与技术方案）  
建立日期：2026-09-16  
状态：产品原始设计，尚未实施  
所属工程：`heat-environment-platform`（独立目录与Git仓库）  
可视化参考：`sunlight-viewer`

本文记录用户已经明确的产品方向，作为后续界面设计、数据接入和开发的初始基线。文中的实时服务、上海场景与UGC功能是建设目标，不表示当前程序已经具备。后续详细设计可以迭代，但应保留本版需求来源与关键决策。

## 1. 产品定位

在 `sunlight-viewer` 的三维可视化基础上，建设面向用户的**可交互式实时热环境探索与主观体感打卡平台**。

用户进入平台后，可以探索当下周边的客观热环境，结合建筑、树冠、绿地、水体、道路等要素理解空间环境，并通过UGC记录和分享自己的热感觉。

研究分析为产品提供模型依据、数据处理方法和验证支持。相关系数、回归表、四象限统计等内容主要属于分析报告或专业入口，不占据用户首页。

产品的两条核心能力：

1. **实时客观热环境视图**：采用和风天气多源气象数据，服务端缓存并持续刷新未来48小时预报序列，支持时间轴选择和空间插值展示。交付要素涵盖温度、湿度、风、露点以及**太阳净辐射（Net Solar Irradiation, W/m²）**；“现在”标为预报驱动估计，各要素均保留其原始空间分辨率与数据来源说明。
2. **UGC主观热暴露打卡**：用户在具体地点和时间记录冷热感受、舒适程度及活动场景，查看附近其他人的体验。

二者在同一地理场景中呈现，分别保留来源、时间和性质，便于用户对照。

## 2. 已确认的设计要求

| 用户要求 | 对应设计约束 |
| --- | --- |
| 面向用户，而非可交互学术报告 | 主交互围绕地图探索、地点查询、查看体验和提交打卡 |
| 客观热环境视图必须实时，采用和风数据 | 获取最新和风逐小时预报，持续刷新并标出有效时刻、获取时间与过期状态；当前时刻显示为预报驱动估计 |
| 按1 km获取48小时预报并缓存、插值 | 在明确展示范围布点，每点一次请求取得完整多要素序列；生成连续图层但不宣称插值提升真实精度 |
| 太阳辐射接入（“有就行”） | 接入和风天气太阳净辐照数据（DWD ICON模式气象场切片，原生像元约8.5 km，z=4），以数据纹理瓦片方式下载并在客户端/服务端解码物理值（W/m²）；通过双线性插值连续表达，并明确标明其宏观气象网格尺度，不与微观建筑阴影混淆 |
| 当前仅两人使用，约10天后展示 | 采用共享后端缓存和调用量预算；点位由展示面积决定，人数与打卡数不决定请求位置数 |
| 结合分析发现的相关因素建模 | 环境因素通过适用模型参与估计；模型用途和验证范围必须明确 |
| 提供UGC主观热暴露打卡 | 形成用户输入、保存、展示、管理和后续分析的完整流程 |
| 沿用sunlight-viewer的基础可视化效果 | 复用三维地形、建筑、树冠、光照、阴影与地理交互的表现方式 |
| 场景叠加其他要素图层 | 提供统一图层管理、显隐、透明度、图例、拾取和时间状态 |

## 3. 研究与产品的时间范围

产品目标区域为**上海市**，主城区若需单独提供场景，须明确边界。

当前已完成的研究分析使用2024年6月1日至9月30日数据。它们用于历史分析、模型开发和验证，不能充当现在的热环境。

实时产品确定采用和风天气，本期以最新48小时逐小时预报支撑当前估计和未来时间轴，接入及账号权限尚待实测。历史2024数据、当前预报驱动估计、未来预报和新UGC打卡分别管理；用户回看历史时才展示对应时期数据，不拿历史研究栅格填充当前视图。

## 4. 典型用户流程

### 4.1 探索当前热环境

打开地图 → 定位或搜索地点 → 查看当前热环境 → 平移、缩放、旋转探索周边 → 点击位置打开环境卡片。

环境卡片优先回答：这里当前估计有多热、数据是什么时候的、估计覆盖什么尺度、附近有哪些近期体感。技术细节通过“数据来源”展开，不挤占主卡片。

### 4.2 查看其他人的体验

打开体感图层 → 查看附近打卡或聚合标记 → 筛选近期、室内外或活动 → 点击卡片查看体验时间、冷热感受、舒适程度及用户愿意公开的补充内容。

旧打卡不会因为用户正在查看实时地图而变成当前体验。列表与标记均显示体验时间，并允许切换查看范围。

### 4.3 记录自己的体感

点击常驻的“记录体感” → 确认地点和体验时间 → 选择冷热感受及舒适程度 → 补充场景 → 提交 → 查看自己的打卡。

定位权限由用户主动触发；拒绝定位时可手动选点。允许记录过去到访的体验，但必须明确填写体验时间，发布时间由系统独立记录。

### 4.4 管理个人记录

在“我的打卡”中查看记录，修改地点、时间或描述，调整可见范围，删除记录。登录与身份方案需在详细设计中确定，第一版也必须能区分记录的创建者和其他访问者。

## 6. 多要素图层

| 图层 | 主要内容 | 展示与交互 |
| --- | --- | --- |
| 客观环境常规气象图层 | 和风温度、相对湿度、风、露点等逐小时预报 | 地表着色、风矢量、图例、时间轴、透明度及位置查询；无UTCI或UTCI分级 |
| 太阳辐射（太阳净辐照） | 和风天气地表太阳净辐照场（DWD ICON数值模式切片，W/m²） | 连续地表色带渲染（0~1200 W/m²）、双线性插值平滑、经纬度数值即时拾取、时间轴联动；标明宏观网格尺度（约8.5 km），与三维建筑/树冠阴影配合展示 |
| 地形 | 经核验的上海高程背景 | 地表起伏与定位参考，说明垂直基准 |
| 建筑 | 轮廓、三维体量和可用属性 | 按需加载、属性拾取、透明显示；估算高度与实测区分 |
| 树冠 | 冠层高度和形态 | 三维冠层、显隐、透明度、来源查询 |
| 太阳与阴影 | 当前太阳位置及场景遮挡 | 跟随时钟模拟；回看时跟随选定时刻；标明模拟性质 |
| 道路与步行空间 | 道路、步道等 | 帮助辨认和探索位置，随缩放调整细节 |
| 绿地 | 公园、绿地等面要素 | 场景覆盖、地点名称、属性与来源 |
| 水体 | 河流、湖泊及其他水面 | 地理语境与属性查询 |
| 公共设施与POI | 饮水、休息、公共室内空间等候选设施 | 类型筛选与地点卡片；缺少开放信息时不声称当前可用 |
| UGC体感 | 用户体验位置、冷热与时间 | 点位、聚合、筛选、详情和个人记录管理 |
| 数据覆盖 | 有效区域、缺测或过期区域 | 轻量提示，区分无数据、未加载、过期与正常值 |

各图层独立提供显隐、适用的透明度、图例和数据来源。点击重叠对象时允许选择目标，避免建筑、树冠或UGC标记永久阻挡地面查询。

热环境值的查询必须对应数据本身，不能从屏幕颜色反推。精细模型叠加粗分辨率UTCI时，地图仍提示UTCI尺度，不能暗示逐棵树下或每条街道的热环境已经获得精确计算。

## 7. “实时”的产品定义

实时意味着利用最新可用输入持续更新热环境，而不是单纯让三维画面、太阳或页面时钟运动。

每次热环境结果需要能够区分：

- 输入气象代表的时刻或时间区间。
- 数据获取和模型计算的时间。
- 结果版本、估计尺度和覆盖范围。
- 是否仍处于配置的有效期内。

本期预报请求默认每60分钟刷新整批48小时数据，按服务实际状态配置调整；不是获取一次后48小时不再更新。逐小时数据不代表10分钟原生数据。当前天气接口为独立可选功能，如启用可按10—30分钟缓存，但不能因供应商当前天气的更新频率而将小时预报标为10分钟实测。界面优先显示预报有效时刻、获取时间及正常/更新中/过期/不可用状态。

| 数据状态 | 用户体验 |
| --- | --- |
| 最新结果有效 | 正常显示，标注代表时刻与来源 |
| 正在更新 | 保留上一版有效结果，显示其时间和更新状态 |
| 数据过期 | 明确显示“最近一次数据，已过期”，不能继续标为当前 |
| 某变量缺失或插值失败 | 对应变量和范围显示暂不可用，不填0；其他有效气象图层、基础场景和UGC可继续使用 |
| 用户选择历史时间 | 明确进入历史模式，显示该时段数据；不同时保持“现在”标签 |

场景更新需要原子切换结果版本，避免颜色来自新版本而点击数值来自旧版本。

## 8. 模型与数据职责

### 8.1 客观热环境

本期常规气象要素数据链为：展示范围约1 km查询点 → 和风逐小时预报（每点hours=48）→ 多要素解析与共享缓存 → 同一有效时刻的空间插值 → 地图着色、风场及数值查询。详见[和风实时气象视图详细设计](和风实时气象视图_详细设计.md)。

**太阳辐射（太阳净辐照）接入机制**：
- **数据源与属性**：采用和风天气气象场数据切片（`layer=asob`，地表太阳净辐照，单位 $\text{W/m}^2$），数据源来自德国气象局（DWD）的 ICON 全球数值天气预报模式，更新步长 1 小时，预报时长 48 小时。
- **数据结构与传输**：该数据以 Web 墨卡托 $z=4$ 金字塔瓦片（$256 \times 256$ 像元，华东区域像元地面分辨率约为 $8.5 \text{ km}$）进行组织。图像底部特定像素行隐写了 28 字节二进制控制头，解析为 7 个单精度浮点数（记录物理量 $Min$ 与 $Max$）；主体网格像元以无符号 8 位整型（$0 \sim 255$）记录在 R 通道中。
- **数值还原与插值呈现**：服务端/客户端通过线性公式 $\text{Value} = \text{Pixel}_R \times \text{Scale} + \text{Min}$ 还原为物理浮点数值，并在前端使用双线性插值（Bilinear Interpolation）消除网格断层感，生成平滑连续的伪彩色辐射图层，支持鼠标点击即时拾取 $\text{W/m}^2$ 数值。
- **与三维微环境及UTCI的协同**：太阳净辐照代表宏观下垫面的大气短波辐射背景场。平台结合三维建筑与树冠模型的太阳阴影计算，可进一步估算局部遮荫率与平均辐射温度（$T_{\text{mrt}}$），从而为后续高可信度的实时 UTCI 计算提供关键物理输入。系统界面明确标明其 $8.5 \text{ km}$ 的宏观气象尺度，不将双线性数学插值伪装为街道级的真实微传感器实测。

局地辐射的具体计算条件见[太阳辐射物理降尺度方案](太阳辐射物理降尺度方案.md)。该方案补充约束上述协同路线：先核验净短波与下行短波的区别，仅有净短波时不直接进行直散分解或生成局地辐射值；取得适用的GHI或DNI/DHI后，再结合建筑、树冠与天空可视条件计算。约8.5 km首先表示上海附近交付瓦片的采样间距，不能据此认定模式原生分辨率。Tmrt与UTCI仍需补充完整辐射输入和独立验证。

建筑、树冠、水体、绿地等可作为局地环境估计的候选因素，但其参与方式应由适用数据和验证确定。几何阴影不能直接赋予任意降温数值，LST不能直接替代Tmrt。缺少细尺度验证时，先提供有依据的空间尺度，不通过插值制造更高精度。

### 8.2 主观体验

既有Logistic模型描述热表达与UTCI、环境因素的关联，输出的是样本条件下的热表达概率，不是客观温度。该模型可以支撑后续体验研究或经验证的辅助功能，不能替代实时UTCI计算。

新UGC首先是用户提交的体验记录，与历史微博分类结果分开标明来源。用户自报选择与算法推断也要区分。后续用于模型更新时，经过质量控制和独立验证，不能将一次打卡立即写成客观热环境真值。

## 9. UGC打卡设计

### 9.1 最小记录流程

| 信息 | 设计 |
| --- | --- |
| 体验地点 | 默认定位后确认，支持地图选点；保存定位来源和可用精度 |
| 体验时间 | 默认现在，允许修改；与系统发布时间分开 |
| 冷热感受 | 冷、凉、中性、偏热、很热；未选择不得默认中性 |
| 舒适程度 | 舒适、一般、不舒适，也可跳过；不由冷热等级自动推导 |
| 所处环境 | 室内、室外、混合或不确定 |
| 活动与现场条件 | 步行、休息、运动、等候等；遮阴、日晒等补充选项，不预选事实 |
| 补充内容 | 可选文字和照片 |
| 可见范围 | 提交前明确展示；对公开精确位置提供隐私选择 |

表单围绕一次具体体验；冷热感受随地点、时间或室内外显著变化时，可分别打卡。第一版不要求用户回答长问卷。

### 9.2 提交后的反馈

按钮应区分正在提交、提交成功、提交失败与待处理状态。失败时保留用户已填内容；重复点击不生成多条记录。用户应能知道自己的记录是仅自己可见、待展示还是已经公开。

公开地图展示经必要内容处理后的记录，支持不当内容反馈。图片公开前处理可能暴露额外精确位置的元数据；原始精确坐标不默认进入公开下载。

近期地图按体验时间过滤；个人页面同时可查看发布时间。地图聚合显示有效打卡数量和冷热构成，不把无打卡解释为无人感到热。

## 10. 在sunlight-viewer中的承接方式

当前工程包含Vite、Cesium和Three.js。已有文档记录 `/cesium.html` 的多源场景，以及 `/` 的样区日照查看页面。历史场景与数据主要对应武汉，不能仅更换标题就宣称已具备上海实时场景。

优先评估Cesium多源场景作为上海地理图层与流式三维内容的承载入口；已有Three.js样区可以保留作局部精细展示。最终入口和组件拆分在详细技术设计中确定，不在本次文档任务中修改路由或替换资源。

可复用或改造的部分：

- 地理场景、镜头、模型加载和对象拾取。
- 建筑、树冠、地形的基础视觉表现。
- 太阳位置和阴影表现，但将模拟时间与气象数据时间分别管理。
- 图层控制、状态提示和移动端布局的可复用结构。

拟新增的能力：

- 上海场景资源及统一坐标配准。
- 实时气象接入、计算任务和热环境发布服务。
- 统一的图层及数据时间管理。
- UGC身份、提交、存储、查询、可见性和记录管理。

后端采用PostgreSQL/PostGIS的既定方向，接口框架与发布方式在后续设计中确定。原始输入、模型版本、实时输出和UGC记录分别管理；前端仅负责交互和展示，不把浏览器渲染阴影作为完整的科学计算服务。

平台的数据表字段、主外键、接口契约和校验规则在 `heat-environment-platform/` 内独立维护，不同步更新研究项目的数据字典。既有[项目数据字典](../docs/项目数据字典.md)仅作为历史研究资产的参考。本文件中的产品信息项不是已建成的数据库结构。

## 11. 第一版范围与实施顺序

1. **场景底座**：确定上海首批覆盖区域，接入建筑、地形、树冠及其他环境图层，完成坐标、拾取和图层管理。
2. **和风实时气象链路**：确认账号权限、上海展示边界与1 km常规气象查询点数量，接入48小时多要素预报及太阳净辐照数据切片，完成共享缓存、小时刷新、插值展示、时间状态和缺测处理。
3. **UGC完整流程**：完成定位/选点、表单、保存、查询、个人管理和必要的公开展示控制。
4. **统一体验**：将地点查询、实时热环境（含太阳辐射）与近期体感整合到同一地图，完善加载、失败、过期及移动端状态。
5. **局地模型扩展**：有验证依据后，将更细的环境因素用于空间估计，再考虑更细尺度或更多体验辅助功能。

可以分阶段开发与演示，但没有真实当前数据接入时，只能标为历史回放或开发演示，不能验收为已实现实时热环境。

## 12. 第一版验收场景

- 用户可以定位或搜索上海覆盖区域，平移、缩放和旋转场景。
- 图层显隐、透明度、图例与拾取结果一致，静态要素和热环境空间位置正确。
- 太阳辐射图层支持0~1200 W/m²连续色带渲染，点击可拾取本地双线性插值解算的真实物理数值，且明确标明其约8.5 km气象网格尺度与DWD ICON模式来源。
- 有新的真实气象输入时，热环境结果按配置更新，地图和地点查询使用同一版本。
- 每点一次预报调用取得48小时多要素；两人查看同一批数据、切换变量、旋转场景及拖动时间轴不额外调用和风。
- 风先转换为分量再插值；湿度、云量等按接口范围处理，缺失和过期不伪装为正常值。
- 用户能辨认结果时刻、有效范围以及正常、过期、缺测状态。
- 当前阴影、热环境估计和主观打卡在展示上可区分；改变太阳模拟时刻不会伪造气象更新。
- 用户可以选点完成打卡，刷新后仍能查询，并能修改或删除自己的记录。
- 近期筛选依据体验时间；历史与实时模式不混用记录和底图。
- 定位失败、网络失败、模型未加载和气象缺失时，仍有可理解的操作与反馈。
- 无样本与热感受为零不同，无环境数据与低热环境不同。
- 图层来源署名保留；公开视图不泄露用户未同意公开的身份或精确位置。

## 13. 待详细设计的问题

和风已确定为本期数据供应方，1 km布点、48小时预报、太阳辐射数据切片接入、共享缓存及多要素展示是已确认方向；上海首批场景边界、最终点数、账号权限、详细插值参数、过期阈值及公开展示许可仍需在实施中确定。基于三维下垫面遮蔽的精细尺度局地辐射/Tmrt模型列为后续扩展。UGC身份方式、公开位置粒度和内容处理规则另行细化。

这些技术与运营选择不改变已经确定的产品方向：**以sunlight-viewer的三维场景为基础，提供多图层的实时热环境探索和UGC体感打卡。**
