# 瓦片背景场时效与分辨率调查记录

- 调查日期:2026-09-19
- 调查对象:`backend/app/services/cloak_tile_service.py` 瓦片抓取 + `spatial_adjustment_service.py` 平差发布
- 证据:`backend/app/data/forecast_cache/tiles/tile_metadata_latest.json`(实际捕获记录)

## 一、问题现象

1. 48 小时平差发布把 +0h ~ +47h 各小时的 API 残差统一加到**同一张背景瓦片**上,但此前元数据不记录瓦片对应哪个预报有效时次,无法评估"背景场时效 vs 预报时效"的错配程度。
2. 由此导致的方法论局限:背景场的**空间形态被冻结在捕获时刻**,只有残差场逐时演化;夜间热岛增强等日变化空间异质性不会随预报时效出现。

## 二、根因调查(基于 2026-09-19T01:29:53Z 实测捕获)

### 1. 有效时次其实编码在瓦片 URL 里,只是旧代码丢弃了它

实测 URL 结构:

```
https://tiles.qweather.com/data/g/2.0/2026091812/2026/09/19/01/2/3/1/rh-2m.jpg
                               └┬─┘ └┬─┘  └───┬──┘ └────┬────┘ └┬┘
                              产品族  版本   起报时次    有效时次  z/x/y
```

- `2026091812` = 模式起报时次(2026-09-18 12Z);`2026/09/19/01` = 瓦片有效时次。
- 捕获时刻为 01:29:53Z(09:29:53 北京时间),各图层有效时次均指向**捕获时刻附近的"当前小时"帧**:rh/wind/dpt/asob 的 URL 写 UTC 小时(01),tmp-2m 写北京时小时(09)——两者是同一瞬时,但**各图层族时区写法不一致**,解析时按 URL 原样记录、不换算。
- 旧抓取代码只从 URL 末段解析 z/x/y,起报/有效时次被直接丢弃 → 48 小时帧共用"抓取时刻"的单一背景,且发布品中无从追溯。

### 2. 附带发现:实际抓到的是低 zoom 祖先瓦片,背景场分辨率远低于设计假设

实测记录:tmp/rh/wind/dpt 为 **z=2, x=3, y=1**,asob 为 **z=4, x=13, y=6**——这些恰好是上海 z8 目标瓦片(8/214/106)的 z2/z4 祖先瓦片(214÷64=3、106÷64=1;214÷16=13、106÷16=6)。

| zoom | 单像元对应经度跨度 | 上海纬度处近似地面分辨率 |
| --- | --- | --- |
| z2(实测捕获) | 90°/256px ≈ 0.35° | **~33 km** |
| z4(实测捕获) | 22.5°/256px ≈ 0.088° | **~8 km** |
| z8(设计假设) | 1.406°/256px ≈ 0.0055° | **~0.5 km** |

成因:页面加载与逐层切换时浏览器会先请求低 zoom 概览瓦片;旧逻辑对同一图层"后到响应覆盖",且每层切换只等 1.5s,最后落网的往往是粗瓦片 → 城市热岛纹理在背景场中被抹平,平差实际变成"大陆级背景 + 控制点残差"。

## 三、已落实的处置(2026-09-19)

1. `parse_tile_url()`:从瓦片 URL 解析起报时次(`run_time`)与有效时次(`valid_time`),连同 z/x/y 一并写入 `tile_metadata_latest.json`,发布品可追溯背景场时效。
2. 同一图层只保留 **zoom 最高**的瓦片,粗祖先瓦片不再覆盖城市级瓦片。
3. 查询路径与浏览器解耦:`solve_spatial_adjustment` / `publish_48h_urban_adjustment_release` 只调用 `load_cached_tiles()`(纯磁盘缓存);浏览器抓取仅在显式维护端点 `POST /api/v1/forecast/tiles/refresh` 或后台任务中发生,避免在 GET 请求内启动数十秒的浏览器自动化。
4. 发布 manifest 的 `quality` 清单加入背景场时效局限声明与本文档指引。
5. 缺测值处理同步收紧:控制点/测试点缺测一律剔除(计入 `missing_*` 字段),不再以常数占位。

## 四、遗留限制与后续方向

- 当前仍为"单一有效时次背景 + 逐时残差"结构;48h 各帧的背景形态不随预报时效变化。
- 若需逐时背景场,可选方案:(a) 驱动和风地图时间滑块逐小时抓取(每次发布浏览器交互量 ×48,脆弱度高);(b) 改用和风/ECMWF 的正规格点 API 产品替代瓦片背景(消耗配额,需重估用量);(c) 用本地高分辨率气象场(如实测站点插值)替代。均需另行评估,未在本轮实施。
